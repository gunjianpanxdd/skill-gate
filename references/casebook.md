# 案例库 · 六道门的真实复盘

> 全部来自真实项目执行记录（2026-11 系列会话），每条标注「哪道门起了作用 / 当初哪里会误判」。判例用于给判定提供锚点，新增案例往这里追加。

## 判例 1：gxdd-doodle 配图规范 → 封 skill（六道门全过的正面案例）

- **过程**：先画 7 幅验收底稿（用出来的）→ 风格规则沉淀为项目 docs → 封用户级 skill。
- **封完仍返工 4 项**：底稿色板违规、笔触越界、class 分裂未记录、深色主题 0 底稿。另发现 skill 间路由冲突（doodle vs oil-visual 同时命中「画个插画」）。
- **复盘**：即使 7 幅之后才封，还是返工——证明「频次门」只能保证大方向，**边界门（负面边界三段式）和校验门（check-style.mjs）才是返工止损器**。返工不是封错了，是封的过程；但若第 1 幅就封，返工会是 7 幅量级。

## 判例 2：AGENTS.md 建了 10 分钟就撤（形态选错的负面案例）

- **过程**：规则散在 README/docs/skill 三处 → 建了 AGENTS.md 收口 → 用户判定单页博客用不上，撤销。
- **沉淀出的判断标准**：AGENTS.md 适合「多命令 + 多禁区 + 多人」项目（如 217 行的 synerza 那份）；单人单页项目属于上下文污染。
- **复盘**：问题不是「要不要沉淀」，是「沉淀成什么形态」。**形态门（阶梯）比"封/不封"的二值判断更常被用错。** 被撤销的知识没有丢——先记进工作日志，这就是阶梯 1 的正确用法。

## 判例 3：openmausbot 整机迁移 → 封 skill（踩坑凝练型）

- **过程**：真实执行一次 7 bots / 2 skills 的迁移 → 过程中查实原方案 6 处实 bug（--dry-run 不存在、per-bot 映射逻辑必失败、丢 scripts、硬编码 UUID 等）→ 修复后才封装为 skill + 打包校验 + 往返实测。
- **复盘**：这 6 个 bug **全部只能在真实执行中暴露**，设计阶段零成本预测。若先设计后使用，6 个 bug 会原样封进 skill。这是「用出来」铁律的最硬证据：**高频次门要求 ≥2 次，本案例 1 次就封了——因为它是执行中已经踩满坑的产物，坑本身就是证据**（高风险例外条款的由来）。

## 判例 4：一篇文章 → deeper-prompt skill（阅读凝练型，六道门部分豁免）

- **过程**：读 Felix Rieseberg 方法论文章 → 核实视频文案与原文偏差 → 封装为双语 skill → 上架 GitHub → 装入 3 个项目。
- **复盘**：这条不符合「执行 ≥2 次」——它的升级证据不是执行记录，而是**用户对该方法论的反复消费意图**（三个项目都要装）。判定时如实标注了「这属于阅读凝练型，频次门以『用户明确确认要复用』替代」。

## 判例 5：user-level skill 同步 3 处副本（维护门的代价实录）

- **事实**：gxdd-doodle 以 user-level 为母本，复制到 pm-os、synerza 两个项目级；改风格规则要同步 3 处，靠 `diff -rq` 校验。且 pm-os 的 .gitignore 分发副本、synerza 的不分发——同样叫「项目级」，分发行为不同。
- **复盘**：封 skill 时没算这笔账，是封完才付的。维护门要求「封之前数清楚要同步几处」直接源于此。**skill 数量 × 副本数 = 变更成本矩阵，这个矩阵在封之前就要摆到桌面上。**

## 判例 6：works.ts 与 index.astro 历史不同步（该沉淀而没沉淀的案例）

- **事实**：博客页数据以内联为准，`data/works.ts` 是镜像，两者曾出现条目不同步（index.astro 有 agents-md-maintenance 条目而 works.ts 没有），本次未补。
- **复盘**：这是「双真相源」结构问题，判定卡应是：**降级落点 = 文档里写死单一真相源声明 + 列入已知不同步清单**，而不是封 skill——同步动作本身是第 2 层文档能解决的纪律问题。
